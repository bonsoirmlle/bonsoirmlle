## 진도보고 양식 (머징 단계)

머징 단계에서 진행 상황을 판단하는 기준은 개인의 자체 완료율이 아니라
**통합 브랜치가 실제로 빌드·동작하는지 여부**임. 아래 3종으로 구성함.

### A. 개인 일일 보고 — 매일 [09:00] 전, 서면 3줄

각 담당자는 아래 3개 항목만 작성함. 서술식 설명은 생략.

1. 어제 머지한 것: [모듈/브랜치명] → [통합 브랜치] / 상태: 머지 완료 · PR 등록(#번호) · 충돌 해결 중
2. 오늘 머지할 것: [모듈/브랜치명] / 예정 시각
3. 막힌 것: [내용] / 대기 대상: [누구의 무엇을 기다리는지] / [며칠째]

3항이 "없음"이면 그대로 "없음"으로 기재함. 3항이 보고의 핵심이며,
이 항목이 비어 있는데 진도가 나가지 않는 경우가 실제 위험 신호임.

### B. 통합 상태 보드 — 통합 담당자 작성, 매일 갱신

| 모듈 | 담당 | 상태 | 통합 브랜치 반영 | 마지막 진전일 | 비고 |
|------|------|------|------------------|---------------|------|
| | | 미착수 / 개발 중 / PR 등록 / 충돌 / 머지 완료 | O / X | YYYY-MM-DD | |

- 통합 브랜치 빌드 성공 여부: [성공 / 실패] — 실패 시 원인 및 담당자 명기
- 미해결 인터페이스 불일치 건수: [건]

### C. 주 1회 통합 빌드 실행 확인

문서 보고가 아니라 통합 브랜치를 실제 실행하여 확인함.
- 일시: 매주 [요일 HH:MM]
- 방식: 통합 담당자가 화면 공유로 빌드 및 실행 시연
- 확인 항목: 빌드 성공 여부, 주요 기능 1개 이상 실제 동작

### D. 인터페이스 변경 통보 (수시)

모듈 간 인터페이스(데이터 형식, 함수 시그니처, 단위·좌표계, 통신 규약) 변경 시
구두 합의로 종결하지 않고 변경 내역을 서면으로 공유함.
머징 단계 장애의 다수는 코드 충돌이 아니라 인터페이스 불일치에서 발생함.

### 보고받지 않을 항목

- 완료율(%) 자체 추정치 — 머징 단계에서는 실제 진도와 괴리가 큼
- "순조롭게 진행 중" 등 근거 없는 정성 평가
- 코드 라인 수, 커밋 수 등 산출량 지표

### 위험 신호 판단 기준

- 동일 담당자의 "막힌 것"이 3일 연속 동일한 경우
- 통합 브랜치 빌드가 2일 이상 실패 상태로 방치된 경우
- PR·머지 요청 없이 개인 작업 브랜치에만 작업이 누적되는 경우
- 인터페이스 변경이 서면 공유 없이 진행된 경우
- 특정 모듈의 "마지막 진전일"이 1주 이상 갱신되지 않는 경우
